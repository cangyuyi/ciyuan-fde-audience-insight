## 二、问题清单（按严重度）

### P1-01：Postgres trigger 可通过 UPDATE 换挂 dataset_version 修改 active/retired 旧快照

**位置**

- `agent/migrations/002_evidence_integrity.sql:21-47`
- 关键缺口在 `:27-37`：UPDATE 与 INSERT 都只取 `NEW.workspace_id / NEW.dataset_version` 并检查其状态；没有检查 `OLD` 记录原属版本。
- 与“即使绕过应用直接修改 active/retired 证据也会被 trigger 阻止”的声明不一致：`agent/README.md:9`、`agent/docs/ARCHITECTURE.md:52-54`。

**确定性复现（SQL 控制流复核；按要求未连接真实 Postgres）**

前置：工作区 `demo` 中版本 `A` 为 active 或 retired，版本 `S` 为 staged；证据 `E` 原属 `A`。

```sql
UPDATE evidence_records
SET dataset_version = 'S',
    content = 'corrupted'
WHERE workspace_id = 'demo'
  AND dataset_version = 'A'
  AND id = 'E';
```

trigger 对 UPDATE 进入 `ELSE`，将目标设为 `NEW.dataset_version='S'`；查询到 `S=staged` 后放行。它从未检查 `OLD.dataset_version='A'` 的 active/retired 状态。结果是旧版本 `A` 丢失记录 `E`，同时 staged 版本收到被污染记录。把 `content` 与版本放在同一 UPDATE 中即可，无需先删除旧记录。

正常 API ingest 路径在 `agent/src/audience_agent/repository.py:169-220` 会先检查当前版本状态，因此该问题不是公开 ingest API 的直接远程绕过；它破坏的是文档明确承诺的**数据库第二道防绕过防线**。利用需要数据库 UPDATE 权限及一个 staged 目标版本。

**影响**

- active/retired 历史快照可被有 DB 写权限的角色改变，破坏证据不可变性、答案 lineage 与审计复现。
- retired 同样受影响。
- 这是核心数据完整性保证未完整修复，故列 P1；因普通 API 主路径已有事务状态检查且利用需要 DB 权限，不列 P0。

**修复建议**

1. 对 UPDATE 同时校验 OLD 与 NEW 所属版本均存在且为 staged；OLD 非 staged 必须直接抛错。
2. 最稳妥的是禁止 UPDATE 改变 `(workspace_id,dataset_version)`，再保留现有 NEW 状态检查。
3. 增加真实 Postgres 集成用例：active/retired 记录分别尝试原地 UPDATE、换挂 staged、DELETE；确认全部失败且旧记录逐字段不变。
4. 继续保持运行角色无权禁用 trigger/约束；数据库 owner 或高权限角色本就超出该 trigger 的防护边界。

### P2-01：readiness 忽略 evidence repository 的 `health() == False`

**位置**

- `agent/src/audience_agent/api.py:248-261`
- `agent/src/audience_agent/repository.py:22-24` 明确定义 `health() -> bool`。

**离线复现**

在 TestClient 运行时把 memory repository 的 health 替换为：

```python
async def health_false():
    return False
repo.health = health_false
response = client.get('/readyz')
```

实测输出：

```text
{'repository_health_returned': False,
 'readyz_status': 200,
 'body': {'status': 'ready'}}
```

原因是 `api.py:254` 仅 `await runtime.repository.health()`，没有保存并判断返回值；`:259` 只检查 checkpoint 与 model。

**影响**

任何遵循 Protocol、以 `False` 而非异常表示未就绪的 evidence adapter 都会被判定 ready，可能使流量进入证据依赖未就绪的实例。当前内置 memory 恒为 True、Postgres 实现成功返回 True/失败抛异常，所以这是潜在契约缺口而非当前内置 Postgres 的已观测实库故障，列 P2。

**修复建议**

保存 `evidence_ready = await runtime.repository.health()`，并将 `not evidence_ready` 纳入 503 条件；补充 health=False、health 抛异常、checkpoint=False、model_not_ready 四种测试。生产探针还应设置短超时，避免依赖连接悬挂拖住 readiness。

### P2-02：limitations 虽不超过 6 条，但强制跨域/M5 安全提示会被可选提示挤掉

**位置**

- `agent/src/audience_agent/graph.py:152-178`

**原因**

先放入最多 4 条模型 limitations，再依次追加无效引用、PII、M5 误述、跨域口径提示；每次只在总数小于 6 时追加。代码注释称“Reserve two slots”，但后续实际有 3 类违规提示和 1 类跨域提示，不止 2 条，因此并不构成完整预留。

**离线复现**

向跨域图注入一个离线模型结果：

- 4 条普通 limitations；
- 1 条有效 M2 claim；
- 1 条无效 citation claim；
- 1 条含手机号 claim；
- 1 条把 M5 观点写成 observation 的 claim。

实测返回 `status='answered'`，最终 6 条为：

```text
限制甲 / 限制乙 / 限制丙 / 限制丁 /
系统已丢弃1条未绑定本次检索证据的主张。 /
系统已丢弃1条包含直接个人标识符的主张。
```

`cross_domain_notice_present=False`，`m5_violation_notice_present=False`。PII claim 与 M5 误述 claim 本身仍被正确删除；丢失的是对应审计提示及跨域口径警示。

**影响**

在恰好最需要完整说明的复杂违规输出中，跨域“不可把单域指标外推为整体人群或漾 YOUNG”提示反而消失，削弱业务防误导与可审计性。未观察到 PII 或 M5 事实化内容因此直接泄漏，故列 P2。

**修复建议**

- 将跨域口径等强制提示放在可选模型 limitations 之前；把三类丢弃计数合并为一条安全摘要，或显式保留足够槽位。
- 明确定义优先级：强制口径/PII/M5 > 其他审计信息 > 模型普通 limitations。
- 新增组合测试：4/5/6 条模型限制 × 三类违规同时出现 × cross_domain，断言总数不超过 6、无 PII/重复且强制提示始终存在。

### P2-03：全字段 PII 防护漏掉 URL workspace_id，且会写入 run lineage/日志上下文

**位置**

- `agent/src/audience_agent/api.py:210-238`：workspace path 只做 `[A-Za-z0-9_-]` 校验。
- `agent/src/audience_agent/config.py:127-165`：API key grant 的 workspace 也未调用直接标识符检查。
- run 记录在 `agent/src/audience_agent/api.py:312-314`，日志携带 workspace 在 `:316-330`、`:352-365`。

**离线复现**

配置一个合法 grant：

```json
{"pii-token":{"workspace":"13812345678","roles":["insight:read"]}}
```

随后请求：

```http
POST /v1/workspaces/13812345678/insights
X-API-Key: pii-token
Content-Type: application/json

{"question":"直播ROI如何计算？"}
```

实测状态为 **200**，并以 `workspace_id='13812345678'` 记录 run。11 位手机号完全符合当前 path 字符集，因此不会触发 422。

**影响**

“全字段 PII”尚未覆盖 URL workspace；在错误配置或把用户标识直接用作 workspace 的部署中，直接标识符会进入请求路径、run lineage 和结构化日志上下文。利用需要服务端预先配置匹配 grant，普通调用者不能仅凭任意手机号绕过 workspace 鉴权，故列 P2。

**修复建议**

在 workspace path 校验和 `Settings.api_key_map()` 启动校验中都拒绝 `contains_direct_identifier(workspace_id)`；422 继续采用不回显 offending value 的统一结构。增加手机号、身份证、email 形式的 workspace 配置/路径测试。
